# The MCP server runs its own LangGraph pipeline

The producer talks to the generator through an MCP client (Claude Desktop / Claude Code). That client is already an LLM and could do the reasoning itself if we exposed only low-level tools (`search_knowledge`, `write_preset`). Instead, the server exposes one high-level `design_patch` tool. It runs a LangGraph pipeline (plan → retrieve → draft → validate → retry → write) on its own Claude API model, plus a small `search_knowledge` tool for follow-up questions. (Retrieval and `search_knowledge` are deferred to v1.1; see ADR 0003.) We chose this so the pipeline is self-contained and testable without a chat client: the eval set runs it directly. Its prompts, model and retry logic are ours to control, not the host's, and it works the same from any MCP client. The cost is a second LLM in the loop, with extra latency and API spend. Don't "simplify" the pipeline away by moving the reasoning into the host.

The pipeline's model is configuration, not code: every node goes through LangChain's chat-model interface, and config selects `anthropic` (default, Claude Sonnet 5.5) or `ollama` (local, offline). Because the pipeline doesn't depend on a chat host, it can also run from a `serum-gen` CLI, and that is the offline entry point: Claude Desktop and Claude Code need the internet even when the tool is local.
