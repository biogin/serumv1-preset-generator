# 10: Revise an existing Preset

**What to build:** You can take any Serum preset and ask for a change in words: "make my 808 hit harder", "less reverb", "darker". You get a new Preset with that change applied and a Patch Recipe that lists only what changed and why ("Dist_Drv 20 → 55 %: more harmonics so it cuts through on small speakers"). The original is never touched.

Decisions (owner, 2026-09-29):
- **Any preset can be revised:** generated ones, the owner's own, and factory presets.
  - Changes are applied on top of the original file, so everything the Patch doesn't model (LFO shapes, FX order, custom wavetables) is kept.
  - Factory presets come from older Serum builds, whose mod matrix can't be rewritten (ticket 05). For those, knobs and switches can change but Routings stay as they are, and the model is told so.
- **The preset is found by name or path.** A name is searched in Serum's preset library (case-insensitive; an exact name wins over a partial match). If several presets match, the result lists them and asks which one; nothing is written.
- **The Revision is saved as a new file** in `User/AI`, named after the original with `_v2`, `_v3`… Numbered names are trimmed to Serum's 31 characters, and nothing is ever overwritten.

How it works: the same LangGraph pipeline, fed the preset's current Patch instead of Init.
- `plan` reads the feedback. The brief carries Constraints as usual, e.g. "harder, but keep the sub clean".
- `draft` sees the preset's current values and Routings and proposes only the changes, plus a "what changed and why" recipe.
- `validate` checks the whole Patch (current values plus changes) against the Parameter Reference and the Constraints, and retries with the errors as usual.
- `write` saves the Revision onto the original's bytes.

Interfaces:
- CLI: `serum-gen revise "<preset name or path>" "<feedback>"`
- MCP: a second tool, `revise_patch(preset, feedback)`, next to `design_patch`.

**Blocked by:** None (can start immediately)

## Comments

- Implemented `revise_patch(preset, feedback)`, the CLI `serum-gen revise`, and the MCP tool `revise_patch`. It is the same LangGraph graph as `design_patch`, run with a job that starts from the preset instead of Init.
- The drafted changes are validated and constraint-checked on the whole revised Patch, then written onto the original's bytes.
- A "Changes" list is computed by code, next to the model's reasons, including readable Routing changes.
- Review fixes:
  - Older-build presets don't store the tail of the second parameter block (Comp_Wet, CompMB L/M/H, LFO1-4 Rise/Delay). Those parameters are now hidden from the model and refused, where before they were silently lost.
  - Presets are rendered before their file is created, so a failed write leaves nothing behind.
  - Unchanged Routing slots keep what Serum stored there (aux source, output knob).
  - The plan prompt no longer repeats its header.
- Live runs with claude-sonnet-5-5 and "make it hit harder":
  - factory `PR 808 Kick Circuit [SD]` → `User/AI/PR 808 Kick Circuit [SD]_v2`: Dist and Comp on, decay shorter, level up (knobs only);
  - `Biggest Hard 808` → `_v2`: more drive, sub and compression, and stronger modulation.
- Name lookup note: after a first Revision, a partial name matches both the original and its `_v2`, so the result lists them and asks. Use the exact name.
- **Still open, needs the owner:** listen to both `_v2` Presets against their originals.
- 2026-09-29: owner A/B'd both Revisions in Serum. Both load.
  - `Biggest Hard 808_v2` hits harder.
  - `PR 808 Kick Circuit [SD]_v2` isn't clearly harder; the owner calls it subjective.
  - The mechanics work. This is a sound-design quality gap: for a kick-style 808 the model shortened the decay and added mild distortion (60 % wet), rather than adding transient punch or loudness.
  - Candidate case for the ticket 09 test set: revise "PR 808 Kick Circuit [SD]" with "hit harder".
